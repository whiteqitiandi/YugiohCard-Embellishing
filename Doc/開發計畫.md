# 遊戲王卡片圖鑑與藝術加工工具：開發計畫

版本：0.4（篩選語意與本機冷門卡標記）

日期：2026-09-01

用途：純個人、離線欣賞；不印製、不商用、不公開重新散布卡圖。

## 1. 結論與技術選擇

採用 **Electron 44 + React 19 + TypeScript + SQLite + CSS/WebGL 分層渲染**。

Electron 仍是本案最合適的主環境。原因不是只為了把網頁包成桌面程式，而是本案同時需要成熟的 CSS 混合模式、遮罩、Canvas/WebGL、離線檔案與資料庫存取、背景更新程序，以及之後的圖片匯出。Electron 44 內含 Chromium 152 與 Node.js 24.18.1；Node 內建的 `node:sqlite` 足以先避開原生套件 ABI 重編譯問題。Electron 官方仍以八週週期發布，因此鎖定大版本並按季升級，不追 nightly。

其他候選：

| 選項 | 優點 | 本案缺點 | 決定 |
| --- | --- | --- | --- |
| Electron | Chromium 視覺技術完整；Node 本機能力成熟；開發速度快 | 安裝體積與記憶體較大 | **採用** |
| Tauri | 體積小、Rust 安全邊界佳 | 系統 WebView 表現差異；資料匯入與圖片管線需更多橋接 | 暫不採用 |
| Qt / C++ | 原生桌面能力強、效能好 | 仿卡片光箔效果、UI 迭代與 Web 生態整合成本較高 | 不採用 |
| 純瀏覽器 PWA | 部署容易 | 大型本機資料庫、多媒體分片、備份與路徑控制不理想 | 不採用 |

正式版 Electron 安全基線：`contextIsolation: true`、`nodeIntegration: false`、renderer sandbox、所有資料庫及下載操作只存在 main process、preload 只暴露窄型別 IPC、外部網址交給系統瀏覽器。

## 2. 已確認的資料來源

### 2.1 建議優先順序

1. **KONAMI 官方卡片資料庫／Neuron**：權威校對來源。官方說明可搜尋全部 OCG 卡、詳細規則與禁限卡表。它沒有面向第三方的大量下載 API 合約，因此不把它當高頻爬取目標；只在增量校對、爭議文字與新卡驗證時低頻存取。[官方卡片資料庫](https://www.db.yugioh-card.com/yugiohdb/card-search.action)、[Neuron 介紹](https://www.yugioh-card.com/en/products/neuron/)
2. **YGOPRODeck API v7**：卡片結構、OCG／TCG 發行日期與異圖清單的主要機器來源。API 正式支援 `startdate`、`enddate`、`dateregion=ocg|tcg` 的發行日篩選。程式只連固定的 `https://db.ygoprodeck.com/api/v7/cardinfo.php`，由使用者指定範圍後才查詢。官方指南要求資料保存在本機、圖片只下載一次，也明定每秒 20 次的硬上限；本專案採更保守的全域單工、每次請求至少間隔 1 秒。[API 指南](https://ygoprodeck.com/api-guide/)
3. **百鴿（YGOCDB）API v0**：自動更新的中文卡名、效果文與日／英文名稱來源。`/api/v0/cardset` 可用密碼批次查詢，單批總數上限 100；回應含 `text.sc_name`、`text.name`、`text.desc`、`jp_name`、`en_name` 等欄位。官方文件也明確標示 API v0 尚不穩定，因此以獨立 provider adapter、固定 endpoint、schema 驗證、回應大小限制與可替換介面隔離；若發行區域要求的語系欄位不完整，該卡不會被標成語系完整。[百鴿 API 文件](https://ygocdb.com/api)
4. **YGOJSON release ZIP**：離線快照與災難備援。它是 MIT 授權的資料結構／匯入工具，整合 YGOPRODeck、Yugipedia 等來源並有固定 schema；使用 release ZIP，不使用其已註明失效／過時的巨大 aggregate raw 檔。[YGOJSON](https://github.com/iconmaster5326/YGOJSON)、[資料模型](https://ygojson.github.io/reference/data-models/)
5. **Project Ignis / BabelCDB / CardScripts**：效果腳本、先行卡、勘誤與規則交叉驗證。CardScripts 自述包含快速先行卡腳本、pre-errata 版本及遊戲專屬卡，適合做差異偵測，不直接把腳本結果當繁中顯示文字。[CardScripts](https://github.com/ProjectIgnis/CardScripts)
6. **salix5 卡片查詢／ygodb**：繁中用詞與查詢體驗的重要人工參考，但目前未見穩定公開 API 與足以涵蓋資料再利用的明確授權，所以不做自動爬取。若日後要批次整合，先取得作者同意或只讓使用者自行匯入。[查詢頁](https://salix5.github.io/query/)、[專案首頁](https://salix5.github.io/)

### 2.2 中英日語系與繁體中文策略

YGOPRODeck 不提供中文，因此它負責語言中立的卡片結構、OCG／TCG 各自發行日、英文名稱與圖片清單；中文名稱、中文效果文及日文名稱由百鴿補足。百鴿目前主要是簡體中文，程式使用 [OpenCC JS](https://github.com/nk2028/opencc-js) 的 `cn → tw` 設定轉成台灣正體，並標記為 `zh-tw-converted`／`machine-draft`，不宣稱是 KONAMI 官方繁中校訂。

卡名匯入採區域感知的必要語系規則：

- OCG 與 TCG 都有發行日期：中文、英文、日文三者均必要。
- 只有 OCG 發行日期：中文、日文必要；英文可保留來源譯名，但不是完成條件。
- 只有 TCG 發行日期：中文、英文必要；日文可為空，畫面標示「未於 OCG 發行」。
- 中文名稱與中文效果文對所有可見來源卡都必要，不以英文冒充中文。

任一必要語系缺漏時，更新器仍匯入同批其他語系完整卡，但連續涵蓋與續傳位置停在第一個缺口。既有人工示範卡的繁中、英文、日文名稱與人工效果文不會被自動來源覆蓋。目前三語完整性針對卡名；效果文以繁中為主要閱讀版本，英文原文保留在 provider 匯入資料，日文效果文要等有明確批次使用條款的穩定來源後再納入正式語系切換。

正式繁中資料仍規劃分成 `official`、`community-reviewed`、`machine-draft` 三種狀態；每筆保留結構來源、中文來源、來源網址、版本、校對人與時間。OpenCC 只能處理字形轉換，卡名、規則術語與一對多字詞仍需以人工詞庫覆寫與校對。

## 3. 收錄範圍

- 收錄 OCG／TCG 中適用 Master Rule（含 VRAINS 後 Link 規則）的卡。
- 可保存 Duel Links／Speed Duel 的差異效果，但它是同一卡片的 `ruleset variant`，不是覆蓋 OCG 文字。
- 不匯入 Rush Duel 專用卡、Maximum Monster、Legend 類型，以及 SEVENS／GO RUSH 專屬規則資料。
- 同名卡的每一幅**不同插圖**均建立獨立 `artwork`；同一插圖在不同卡包、稀有度或卡號印刷則建立多筆 `printing`，共同參考同一 artwork，避免重複 BLOB。
- Token、Skill Card、動畫原創卡預設排除；日後可做獨立收藏資料集，不能混入主要 OCG 搜尋結果。

## 4. 資料庫與媒體儲存設計

### 4.1 不把 14,700+ 張卡圖做成離散檔案

正式資料目錄：

```text
ArcanaArchive/
├─ catalog.sqlite                 # 全部文字、索引、關聯、版本與媒體清單
├─ staging/                       # 更新驗證中的暫存 DB
├─ media-shards/
│  ├─ media-series-01.sqlite      # 卡圖 BLOB 分片
│  ├─ media-series-02.sqlite
│  └─ ...
└─ backups/                       # 上一版 catalog + manifest，不複製所有媒體
```

文字庫採單一 SQLite（WAL、外鍵、定期 `PRAGMA integrity_check`）。卡圖放在多個 SQLite BLOB 分片，不產生數萬個離散檔。分片鍵以「首次收錄產品系列／發行年代」為主、固定上限為輔；一個分片建議控制在 512MB～1GB，超過就建立下一卷。卡包只是 printing 分類，不能直接拿每一包做一個 DB，否則同一插圖重印會造成重複與過多小 DB。

每個媒體項目保存 `sha256`、MIME、原始 URL、抓取時間、像素尺寸與位元組數。程式啟動時只開 `catalog.sqlite`；使用者真正查看某張卡圖時才開對應分片。分片損壞只影響有限卡圖，可依 manifest 重新下載，不拖垮文字庫。

### 4.2 核心實體

| 實體 | 主要用途 |
| --- | --- |
| `cards` | 穩定邏輯卡 ID、密碼、KONAMI ID、數值、種族、屬性、框型 |
| `card_texts` | 語言、名稱、效果、來源、校對狀態 |
| `rule_texts` | `ocg-master`、`duel-links-speed` 等規則版本與有效期間 |
| `artworks` | 同名卡的每一幅插圖與媒體分片指標 |
| `sets` / `printings` | 卡包、卡號、稀有度、地區、發售日、使用的 artwork |
| `effect_tags` | 直接傷害、貫通、抽牌、檢索、送墓、破壞、除外、特殊召喚等正規化標籤 |
| `archetypes` / `card_relations` | 青眼、黑魔導、碼語者等系列與角色／主題關聯 |
| `compatibility_traits` | 等級、種族、通常怪獸、攻擊力區間等可計分適配特徵 |
| `source_records` | provider、遠端 ID、版本、ETag、雜湊、授權備註 |

搜尋使用 SQLite FTS5 + 正規化表，不把全部標籤塞成逗號字串。適配性採可解釋計分：系列明確支援 > 效果條件完全相符 > 屬性／種族／等級等特徵相符 > 統計共現。每筆推薦要能列出理由，為未來 D 功能打底。

目前雛型先在 `cards` 保存 `source_name`、`source_url`、`localization_source_name`、`localization_source_url`、`localization_status`、`release_region`、`release_date`、`ocg_release_date`、`tcg_release_date`、`is_unpopular` 與 `imported_at`。`is_unpopular` 是純本機使用者偏好，來源更新不得覆寫。`app_meta` 分別保存 OCG／TCG 的 `complete_through`、`resume_month`、`resume_offset`、目標月份、狀態與說明。`complete_through` 的語意固定是「已完整收錄到哪個卡片發行日」，不是程式何時執行更新；`last_card_update_at` 只作技術稽核，不拿來顯示收錄進度。正式 `source_records`、`sets`／`printings`、FTS5 與校對狀態正規化仍列在 Phase 1 後續工作。

### 4.3 篩選語意與冷門卡片

- 卡片大類、卡片細分、屬性、種族都是離散欄位，同一欄位多選固定採聯集（OR），不提供排除或交集開關。
- 不同基本欄位之間固定採交集（AND），例如「怪獸卡 AND 暗屬性 AND 龍族」。
- 怪獸／魔法／陷阱細分合併成同一個「卡片細分」群組，因此「同步怪獸＋速攻魔法」能正確表示兩種細分的聯集，不會形成不可能的跨群組交集。
- 只有效果標籤支援納入／排除；納入多個效果時可選任一符合（聯集）或全部符合（交集），排除永遠優先。
- 使用者可在卡片詳情切換「冷門卡片」標記。標記保存於本機 SQLite，常用篩選可保存「顯示全部／隱藏冷門／只顯示冷門」三種模式；不修改或回傳任何來源資料。
- 舊版常用篩選的怪獸、魔法、陷阱細分會在讀取時合併到新群組；基本欄位舊有排除／交集設定因語意已廢止而安全正規化為聯集。

## 5. 更新與禮貌存取策略

已落地的行為：

1. 啟動時完全不連線。更新功能位於獨立的「資料更新中心」；只有使用者明確選擇模式、OCG／TCG、年份與月份並送出後才連線。
2. 支援「指定單一月份」以及「截至 A 年 B 月（含）的所有卡片」。後者從各地區的連續涵蓋游標接續：OCG 預設由 1999-01、TCG 由 2002-01 開始，逐月查詢，不先抓全庫再於本機篩選。
3. 各來源使用獨立而且跨月份有效的流量政策：

   | 來源 | 用途 | 批次 | 最小間隔 | 每次執行上限 |
   | --- | --- | ---: | ---: | ---: |
   | YGOPRODeck | 結構、發行日、圖片清單 | 100 張 | 1 秒 | 40 請求；單月另限 1,000 張 |
   | 百鴿 YGOCDB | 中文名稱與效果文 | 100 張 | 2 秒 | 5 請求／500 張 |

4. 全域只允許一個更新工作。每頁另設 30 秒連線逾時與 12MB 回應上限；429 會停止並提示稍後再試。圖片下載是另一條單工、按需快取管線，不占文字更新配額。
5. 「截至月份」碰到任一內部上限時，只處理至上限，依發行日／卡片密碼排序保存最後可證明完整的發行日與月內續傳 offset；若下一張與上一張是同一發行日，就不會提早宣稱該日完整。下一次由該位置繼續，未完整處理的範圍不會誤標為完成。畫面顯示的是卡片發行涵蓋日，程式執行完成時間只存在結果稽核欄位。
6. 每個月份的結構頁必須完整讀取後才進入語系合併。程式以 YGOPRODeck 的 `ocg_date`／`tcg_date` 判定必要語系；若中途缺少中文、英文或日文必要欄位，該卡不匯入，連續涵蓋與續傳游標停在第一個缺口。同批後方已符合區域語系規則的卡仍可收錄，但不能讓涵蓋日期越過缺口。
7. 遠端 JSON 經 schema／ID 驗證後，才以 SQLite transaction 合併該批資料。Rush、Skill Card 與 Token 預設略過；以密碼合併既有人工卡時保留人工繁中與效果文。
8. 圖片不隨更新批次下載。只有真正查看插圖時才由 `images.ygoprodeck.com` 下載一次，經 allowlist、8MB、MIME 與 SHA-256 檢查後存入本機媒體分片。

後續正式化仍需加入 `checkDBVer.php`／ETag manifest、staging 檔案、可復原備份、503 與 `Retry-After` 指數退避、少量 jitter、完整 schema 差異報告，以及 YGOJSON release ZIP 備援。`checkDBVer.php` 適合未來的「檢查是否有任何變更」功能；使用者已明確指定月份時不額外呼叫它，以減少一次不必要請求。

## 6. Duel Links 加工研究與復刻方式

KONAMI 官方的 Chronicle Card 說明確認有四種 Special Processing Item：**Surface Processing、Rim Color、Name Color、Stamp**，而且它們是彼此獨立的加工類別。[官方活動說明](https://www.konami.com/yugioh/duel_links/en/campaign/gorush-world/) 8 週年官方活動則明列 Gold Name、Gold Rim 與 Aurora Surface；後續官方活動亦出現 Animated、Luminous 與 Full Starlight。[8 週年公告](https://www.konami.com/games/eu/en/topics/18415/)、[World Update 公告](https://www.konami.com/games/ca/en/topics/3005/)

雛型不是擷取 Duel Links 貼圖，而是復刻其視覺原理：

```text
游標／未來陀螺儀
      ↓
入射光座標（CSS custom properties）
      ↓
繁中卡片基底 → 卡圖 → 卡名/邊框/印章 → 表面遮罩 → 反光 → 顯示/匯出
```

- **Crystal**：重複多邊切面／conic gradient，`color-dodge` 混合。
- **Aurora**：大範圍 conic/radial spectrum 隨光源移動。
- **Starlight / Full Starlight**：點狀遮罩 + 斜向光束；滿版版提高密度並覆蓋全卡。
- **範圍**：整卡、圖片區、外框使用獨立 CSS mask；卡名與邊框永遠是獨立層。
- **效能階梯**：列表縮圖只用靜態 CSS；單張預覽啟用動態 CSS；需要動畫、視差深度、凹凸／粗糙度貼圖時才切 WebGL shader。低階 GPU 或 `prefers-reduced-motion` 自動降級。

未來 C 功能直接輸出同一個 `CardRenderModel`，所以自訂卡不是另一套畫圖程式；名稱、圖片、框型、數值、效果文字完成排版後，原封不動進入同一加工管線。

- Windows 雙擊安裝、啟動、重建與安全清理批次檔。

雛型資料是資料模型與互動驗證樣本，不宣稱完整或最新；效果文字中標註「雛型」者，上正式資料前需以官方資料庫校對。

## 8. 開發階段

### Phase 1：圖鑑核心與來源匯入

- **已完成第一段**：增量 migration、雙 provider adapter、單月／截至月份匯入、OCG／TCG 獨立連續涵蓋游標、不同來源流量政策、區域感知的中英日卡名完整性、基本欄位／效果分離的篩選語意、本機冷門卡標記、transaction 寫入、來源欄位與插圖按需快取。
- **待完成**：FTS5、獨立 `source_records`、檔案型 staging／rollback、`sets`／`printings` 與跨印刷 artwork 去重。
- 以使用者選定月份匯入可控子集；後續再提供主角王牌系列／卡包選擇，驗證 printing 去重。
- 建立繁中術語表、校對介面、Rush 排除測試與來源差異報告。
- 驗收：離線搜尋、重啟持久化、更新失敗不破壞舊資料、任一媒體分片損壞仍可瀏覽文字。

### Phase 2：藝術加工正式化

- 依參考畫面調校 Crystal／Aurora／Starlight；補 Noise、Sepia、Damaged、Animated 等效果。
- 加入 mask 編輯器，支援圖片區、標題、框、文字區與自訂遮罩。
- Canvas/WebGL 匯出 PNG/WebP；色彩管理、不同 DPI 與無動畫快照。
- 驗收：60fps 單卡互動、縮圖不啟用昂貴 shader、各框型排版不溢出。

### Phase 3：卡片創作（C）

- 表單、即時排版、自訂卡圖、框型、星級／階級／Link、靈擺刻度與完整效果文字。
- 自訂卡與官方卡分開 namespace、分開 DB，禁止更新器覆蓋。
- 沿用 Phase 2 加工與匯出。

### Phase 4：牌組分析／自動組裝（D）

- 先做可解釋的規則式分析：曲線、起手率、檢索鏈、死抽、召喚條件、手坑與解場比例。
- 再用標籤圖譜與卡表共現資料做候選排序；禁限表、格式與預算是硬限制。
- 自動組裝最後才導入搜尋／最佳化，不一開始使用不可解釋的生成結果。

## 9. 風險與界線

- 「個人非商用」不等於取得卡圖、卡框與文字的再散布權。本機快取可符合個人用途，但發佈安裝包時不夾帶卡圖與大量卡文；讓使用者自行下載，並保留來源與刪除機制。
- KONAMI 官方站是權威校對來源，不代表允許批次爬取。若沒有公開 API，維持低頻人工驗證。
- YGOPRODeck 的資料與服務長期可用性不是保證，因此保留 provider adapter、YGOJSON 快照、來源版本與可重建 manifest。
- `node:sqlite` 在 Node 24 仍標示 release candidate；若 Electron 升級造成回歸，替代方案是 `better-sqlite3` + 固定 Electron ABI 與 rebuild 流程，資料 schema 不需改變。[Node SQLite 文件](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html)
